# Living Dex: agent guide

A camera-first "real-life Pokedex" for iOS 26: point the camera at anything alive, get a rarity-graded card for the Dex. UIKit, GRDB (`App/Database`), Swift 6 with complete strict concurrency. `README.md` describes the features and the demo and store-asset tooling; this file is the working guide.

## Build and test

```sh
xcodegen generate
xcodebuild test -project LivingDex.xcodeproj -scheme LivingDex -destination 'platform=iOS Simulator,id=<udid>'
```

Run from the monorepo as `apps/living-dex`; the mirror is `guitaripod/livingdex` (`midgar sync living-dex`). Bundle id `com.guitaripod.livingdex`, registry slug `living-dex`.

## Midgar platform

- **Packages.** MidgarKit comes from the monorepo's `packages/MidgarKit` by path and AICredits from `packages/AICredits` by path, both in `project.yml` (decision D15). The app links AICredits' `AICreditsCore` only: RevenueCat is gone from the app (no import, no key, no linked product), and `purchases-ios-spm` appears in a generated `Package.resolved` only because `packages/AICredits/Package.swift` declares it for the apps that use `AICreditsRevenueCat`.
- **Composition root.** `LivingDexMidgar` (`App/`) builds the Midgar ID (`MidgarIdentity`, no App Attest entitlement), the purchase engine (`store`, a `MidgarStore`) and the credit wallet (`credits`, a `MidgarCredits`), the gateway addresses, the portal configuration and the log file. `store` and `credits` are nil in a test host or a demo capture, as `reachesMidgarServices` decides. The keychain groups are the app's own first, then `$(AppIdentifierPrefix)cc.midgarcorp.shared`.
- **Commerce.** The commerce engine is `storekit2`. One `MidgarStore` (mode purchases) sells Living Dex Pro and the credit packs, and `MidgarCredits` holds the balance on the Midgar ID wallet. `App/Credits/LivingDexPacks.swift` is the one table the store configuration, the credits configuration and the tests read: Pro `com.guitaripod.livingdex.pro.monthly` $4.99 and `.annual` $29.99 (one group, "Living Dex Pro", a 3-day free trial on the annual plan) both granting entitlement `pro`; packs `starter` 100 credits $2.99, `regular` 400 $9.99, `propack` 1200 $24.99 ("Explorer"), `science` 2600 $49.99 ("Naturalist"), products `com.guitaripod.livingdex.credits.<id>` (mako requires its `rc_product_prefix` plus the pack id). Never change product ids, prices or credit amounts without the founder. A purchase carries the Midgar ID as `appAccountToken`; MidgarCredits posts a pack's signed transaction to mako's validate route, which verifies it and credits the wallet under the key the webhook shares, so a credit lands once. MidgarCredits runs in legacy-key mode: `legacyAPIKey` is the AICredits api key (`AICreditsManager.legacyAPIKey()`), so the balance from before the move stays linked and the requests carry `Authorization: Bearer <key>` plus `X-Midgar-Token`; its `X-App-ID` is the registry slug `living-dex`, the AI calls keep the tenant `livingdex`.
- **Pro.** `ProAccess` (`Features/Paywall/`) is the observable Pro model: `isPro` is `store.isEntitled(to: "pro")`, read at launch and on every `entitlementsChanged`, after a purchase and after a restore, so Ask to Buy unlocks by itself when approved (the open paywall dismisses), a refund or a lapse takes Pro away, and a subscription bought through RevenueCat before the move is an Apple transaction that StoreKit's current entitlements already cover, with no network. The last answer is kept in `ProEntitlementStore` and seeds `isPro` at the next launch. `ProAccess` also calls `reportPurchaseHistory()` once per install so those subscriptions reach the Midgar ID in the ledger. The paywall keeps its layout, copy and plan order (annual first); plans, prices and the free trial come from StoreKit through `MidgarStore.products()` and `MidgarTrialPolicy` (`ProPlanQuote`, `PaywallPlan`). mako's premium check (Pro bypasses the credit meter) asks the ledger for the Midgar ID first and RevenueCat by mako user id second, so the app sends no premium header.
- **Credits.** `CreditsModel` (`App/Credits/`) wraps MidgarCredits for the UIKit screens (`knownBalance`, nil until a read has succeeded, published as `knownBalancePublisher`): read at launch, on foreground, after every identification that reached mako and after a restore, and it follows `events()`. The store is MidgarKit's `MidgarCreditStoreView` inside `CreditStoreSheet` (`Features/Credits/`), opened from the paywall's "Buy identification credits". An identification that mako refuses for credits is `IdentifyError.creditsExhausted(shortfall:)` (`CreditShortfall`); the Field alert opens the paywall with it and the paywall passes it on to the store's banner. Demo captures use `DemoCreditsSource` (a fixed balance, no network) and fixed plans.
- **Account deletion.** `LegacyAccountDeleter` deletes the old per-app account through `MidgarCredits.deleteLegacyAccount()` (AICredits' own delete when there is no wallet), then the local AICredits identity and data are cleared in the existing order; a failure leaves everything local in place. A 404 from mako now counts as already deleted, with 401. The Midgar ID and the subscription stay.
- **StoreKit testing.** `Products.storekit` at the app root holds the four packs and the Pro group and is the Run action's StoreKit configuration (`project.yml`). `CreditsPurchaseStoreKitTests` and `ProPurchaseStoreKitTests` run under `StoreKitSuites` (serial) against a `URLProtocol` stub of the gateway (`CreditsGatewayStub`). A purchase in the test host needs a window scene (`hostScene()`), and a finished consumable is read from `session.allTransactions()`, not `Transaction.latest`. StoreKit tests need the iOS 27.1 runtime with the iPhone Duo device type, and the first purchase on a fresh simulator can stall, so rerun once.
- **Gateway.** mako is `https://api.midgarcorp.cc/v1/intelligence` (`LivingDexMidgar.intelligenceURL`, AICredits' base URL) and AICredits sends the Midgar token through `additionalHeaders` (`midgarTokenHeaders()`, never waited on); MidgarCredits takes the plain `MidgarHTTPConfiguration(appID:)`. The worker is `https://api.midgarcorp.cc/v1/livingdex/...` through `LivingDexGateway`, each call once with the timeout it always had (3.5 s enrichment, 8 s Regional Dex and call lookup). The worker is keyless and the gateway forwards no `Authorization` to it, so worker calls carry none. The tenant id is `livingdex` (mako and the worker know the app by it); the Midgar ID, signals and the portal use the registry slug `living-dex`.
- **Species verification.** The worker answers 404 with a plain `{"error": ...}` for a name GBIF rejects, which `SpeciesEnricher` reads as "unresolved" and never mints; a 404 with an error code is the gateway's own and only makes the result unavailable.
- **Logging.** `MidgarLog` writes `Library/Logs/livingdex.log` (the name `ios-device-logs` pulls). Categories are in `App/Logging`. Never log photos, prompts, model output, coordinates or tokens.
- **Settings.** `SettingsViewController` hosts MidgarUI's `MidgarSettingsViewController` with the portal card (`LivingDexMidgar.portalConfig`) in `MidgarTheme.livingDex`.
- **Reviews.** `ReviewPrompt` reports a saved new Dex entry to `MidgarReviewPolicy` and asks StoreKit only when it allows.
- **Legal.** Policy and terms live at `https://midgarcorp.cc/legal/living-dex/{privacy,terms}/` (`LegalLinks`); the source is `web/midgarcorp/src/content/legal/living-dex/`. Keep `Resources/PrivacyInfo.xcprivacy`, `store/privacy-label.md` and the policy in step.
- **Worker** (`services/living-dex`, `livingdex-worker`): GBIF rarity, Regional Dex and species call. Deploy it and the gateway before an app release that depends on a route.

## Layout

`App/` (entry point, composition root, services), `Features/<Feature>/` (view controllers), `Core/LivingDexCore` (Swift package: `Rarity`, `Realm`, `XP`, `Level`, `ProgressEvent` and the identification candidate types, no UI imports; `swift test` inside it), `Resources/`, `Tests/LivingDexTests`.

## Rules

No inline comments (a `///` on a well-named method instead), no file headers, no file over 1,000 lines, `midgar arch check --app living-dex` with 0 errors.
